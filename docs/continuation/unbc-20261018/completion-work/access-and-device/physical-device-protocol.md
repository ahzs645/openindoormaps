# Real-phone and venue verification protocol

Status: no physical phone is connected to this environment. `device-capabilities.json` records the actual capability inspection. Existing cloud Chromium and mobile viewport checks are software/browser evidence only. This protocol is ready for an identified real-device operator; its unperformed steps are not a pass.

## Freeze the test target

1. Record tester, date/time/timezone, actual phone manufacturer/model, OS version, browser/version, screen orientation and network type. Record the deployed HTTPS URL and release receipt, source ZIP SHA-256, dataset SHA-256, routing engine SHA-256 and directions-runtime SHA-256. Obtain these from the actual release; never substitute a historical receipt.
2. Agree launch, first-map, route and interaction performance budgets before running. Keep the agreed budgets in the result. A missing budget cannot yield a performance pass.
3. Use a private tab or clear that site's storage. Capture a screen recording from before navigation. Record cold elapsed timings separately from warm elapsed timings. Do not claim precise memory measurements without device/browser instrumentation.

## Remote UI tests on the phone

| Test                | Required observation                                                                                                                                                                                                                                                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cold visitor entry  | Open the prepared indoor-project entry; observe useful progress and an interactive map, search and building/floor controls. Record first visible content, first useful map and usable search times. No tab reload, browser crash or endless progress.                                                                                                                        |
| Floor scope         | Open each advertised default floor and return to Main. Check the intended floor label, visible geometry and selection; record scope IDs. | Same-floor request  | Search 05-136 Library Services Desk → 05-173 Classroom; choose start and destination, calculate, read/advance every instruction and inspect arrival. Repeat reverse. Record stable keys from `physical-test-place-identities.json`, displayed warning text and elapsed route time. A route with unknown access is diagnostic evidence, not a confirmed-public qualification. |
| Cross-floor request | Request the source-bound 05-143 Lobby → 05-242 Lobby pair. Inspect every displayed floor transition and step-free profile result. Record connector identity, warnings or refusal. Do not assume an elevator exists at both stops solely from the labels.                                                                                                                     |
| Ramp request        | Request 07-180 → 08-S101 in walking and step-free profiles. Record the actual selected connector, route warnings/refusal and arrival. Preserved user ramp decisions do not establish building-code compliance.                                                                                                                                                               |
| Refusal behavior    | Request a staff room from a known public endpoint and an impossible/invalid endpoint pair. Observe a clear refusal and a usable recovery path, with no invented straight-line route. Switch profile and endpoints afterwards to detect stale warning/result state.                                                                                                           |
| Share/reload        | Copy an actual route link, open a new phone tab, confirm endpoint/profile/floor restoration. Test browser back/forward and invalid/stale room keys. Invalid data must not silently select an unrelated room.                                                                                                                                                                 |
| Interrupt/recover   | Cancel during a cold load, retry, change floor while loading, leave browser for 30 seconds and return. Record whether work resumes safely and UI remains usable. Disable network after a warm load: record which actions remain available, and whether failures explain retry. Offline availability is a separate result, never assumed.                                     |
| Touch and text      | Portrait and landscape, device text enlargement, keyboard open, long search result and long instruction. Confirm readable instructions, scrollable results, reachable close/back/profile controls and no horizontal clipping or map gestures trapping controls.                                                                                                              |

Repeat on each phone/browser platform advertised for release. A single real iPhone does not establish Android support, or vice versa. Save recordings/screenshots, elapsed-time notes and a per-test result referencing the frozen release. Do not place personal or patient data in captures.

## Separate on-campus route/access verification

A remote phone UI test cannot establish door access or on-campus accessibility. A venue-authorized reviewer must walk each route intended to be advertised, checking the exact endpoint entrance, every source owner and hidden physical-door dependency listed by the access audit, connecting floors, current elevator stops/service, opening schedules and audience restrictions. For a step-free claim, document the approved evidence for every edge's width, threshold, slope, landing, turning space and lift requirements. Record limitations, evidence reference, reviewer identity/date and review expiry in the source-bound checklists. Preserve staff boundaries and refusals.

Hall A–Q already has an explicit original user decision. Its original legend must be bound to stable source identities or geometry before applying it; this is recovery of its scope, not a request to approve those halls again. Any geometry change needs its own current source validation. Re-run the access-only CLI, geometry release checks and real-phone scenarios against the resulting exact release.

Use `physical-device-result-template.json`. Null measurements and `not-run` outcomes stay null/not-run until an actual operator records them. Attach a venue access review separately. A report may pass phone UI checks while venue access qualification remains incomplete.
