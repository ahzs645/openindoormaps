# Post-compilation current stair-policy strengthening

This is a proposed, unadopted validation sequence. The running native compilation retains its historical 946-file closure. No production source, physical kernel, compiler output or publisher pin was changed for this review.

The old v2 consumer omitted current routing semantics on complete flat receipt approaches. Its old4f lower cell 868 carries 27 ordinary-room dependencies absent from the stair edge. Historical calculator and worker outputs demonstrate that the incomplete consumer calculated a route; they do not establish qualified public navigation. The additive guard must refuse that old case. Its original-RVT physical proof remains separate authoring evidence.

## Boundary that can be separated

`prepareIndoorDataset` starts with an empty edge inventory and constructs the native graph. It does not construct `nativeSteppedStairV2` variants. The frozen driver subsequently calls the separate source finalizer on the completed cells and graph. That boundary permits **revalidation of exactly the already-compiled operands**, provided every saved pre-finalizer field hash is reproduced. It does not prove a newly modified native compiler would emit the same output, and must not be described as a fresh compilation under new code.

Reviter's qualifier is a source/physical layer. It has no counterpart to OIM's `nativeCellAccessIsSupported` or `projectLinkPolicy`. Keep Reviter, source producer/constructors and physical kernels unchanged. Add the current transit guard to the OIM consumer only; do not claim new cross-repository consumer-policy parity.
