# Indoor viewer data models — unification notes

Field-level survey of how three commercial indoor viewers model pathfinding,
vertical transitions (stairs/escalators/elevators) and stores, compared with
this repo's model. Vendor demo venues are ported as native fixtures
(`app/data/city-mall`, `app/data/harrods`, `app/data/mappedin-mall`,
converters in `scripts/port-*.py`); only names, categories, footprints and
transition positions are vendor data — routing graphs are synthesized from
that geometry (spine + spurs + vertical edges) and transitions missing from
a capture are marked `(inferred)`. The synthetic `galleria` demo location
(`app/data/galleria/`) expresses every pattern below in our own format and is
regenerated by `scripts/generate-galleria-fixture.py`.

## OpenIndoorMaps (this repo)

- **Units/stores**: GeoJSON Polygons, `properties.feature_type: "unit"`,
  `level_id`, numeric `id` (used for click → POI resolution via point-in-polygon
  in `app/utils/poi-map.ts`), optional `category`.
- **POIs**: Point features, `{id, name, type, floor, building_id, metadata}`;
  name-indexed by MiniSearch (`app/utils/indoor-geocoder.ts`).
- **Routing graph**: built client-side from LineString features
  (`app/indoor-directions/directions/main.ts:201`). Each segment is an edge;
  vertices are exact coordinate matches (floors connect where a vertical
  connection's endpoint XY equals a corridor node XY).
- **Edge metadata** (`app/indoor-directions/types.ts:4`): `level_id`,
  `network_type`, `access_type`, `is_accessible`, `cost`,
  `vertical_connection_id`, `from_level_id`/`to_level_id`.
- **Accessibility**: `accessibleOnly` pathfinding option skips
  `is_accessible: false` edges; `stairs`/`escalator` default to inaccessible
  (`main.ts:157`).
- **Cost**: `properties.cost` overrides geometric distance as edge weight
  (`main.ts:187`) — this is where transition travel times live.

## Pointr (capture: recovered/pointr, SDK v9.9.0)

Fully captured. Venue payload is a GeoJSON FeatureCollection (~992 features for
the demo venue). Ported to `app/data/harrods` (`scripts/port-pointr-harrods.py`):
8 levels, polygon POIs as units with descriptions/logos. Concession brands
share their department's exact footprint (one map polygon, one searchable POI
per brand). Transition nodes (class `path`) are absent from the POI payload,
so shafts reuse real vendor evidence: the escalator (L-1 → L0, up-only) and
elevator positions from the captured route-engine sample, plus one inferred
staircase.

- **Stores/POIs**: one flat feature list; Polygon (unit) and Point (POI)
  features share one property schema:
  - identity: `fid` (feature), `sid`, `bid` (building), `lvl` (level), `eid`
  - classification: `typeCode` (e.g. `restaurant`, `restrooms`,
    `entrance-exit`, `parking-spot`, `atm`, plus retail categories like
    `womens-clothing`), `keywords`, `tags`, `group`
  - rich metadata: `logo`, `imageUrl`, `images`, `openingHours`, `phone`,
    `link`, `booking`, `video`, `rating`, `description`
- **Type registry** (captured JSON, 464 entries): per-`typeCode` metadata —
  `typeName`, `description`, `categories`, `isMapObject`, `shape`
  (`polygon,point,line`), `class` (`path` for transitions), `isWalkable`.
- **Vertical transitions** are type entries with explicit semantics:

  | typeCode                 | transitionDirection | isTransitionAccessible | transitionTravelTime (s) |
  | ------------------------ | ------------------- | ---------------------- | ------------------------ |
  | `stairs-node`            | bidirectional       | false                  | 60                       |
  | `escalator-node`         | unidirectional      | false                  | 45                       |
  | `elevator-node`          | bidirectional       | **true**               | 120                      |
  | `custom-transition`      | bidirectional       | false                  | —                        |
  | `building-entrance-exit` | bidirectional       | true                   | 1                        |

- **Route response**: `{directions: FeatureCollection, nodes: [...],
distanceMeters, timeSeconds}`. Turn-by-turn direction features carry
  `message`, `distanceUntilMeters`, `timeUntilSeconds`, `turnAngleRadians`,
  `transitionInfo`, `type`, `lvl`, `bid`, `sid`.

**Mapping to our model**: `typeCode` → POI `type`/`metadata.category`;
`transitionTravelTime` → edge `cost`; `isTransitionAccessible` →
`is_accessible`; `transitionDirection` → not yet supported (our graph edges are
bidirectional — see gap list).

## Situm (capture: recovered/situm-fixed, viewer 1.213.8)

Ported to `app/data/city-mall` (`scripts/port-situm-citymall.py`): "City Mall"
building 7033, floors -1/0/1, vectormap footprints (53 shops, stairs,
elevators, corridors) joined to the 120 named indoor POIs by proximity, 9
cross-floor transition shafts. Turn-by-turn "indications" enum observed in the
viewer bundle: `INITIAL`, `TURN`, `TURN_SLIGHT`,
`CHANGE_FLOOR`, `DESTINATION_REACHED`, `END` — a floor change is a first-class
navigation instruction. **Accessibility**: `accessibilityMode` with
`CHOOSE_SHORTEST` / `ONLY_ACCESSIBLE` — equivalent to our `accessibleOnly`
flag. Routing runs in a Web Worker (~500 KB `worker-*.js` bundle references
stairs/elevator/ramp/steps); rendering via deck.gl layers (`FloorPlanLayer`,
`PoiLayer`, POI categories).

## Mappedin (capture: recovered/mappedin)

Demo-mall payloads captured from the public api-gateway (`map`, `polygon`,
`location`, `theme` for `mappedin-demo-mall`, 2 floors, 343 polygons, 269
locations) and ported to `app/data/mappedin-mall` (`scripts/port-mappedin-mall.py`).
Pixel vertexes convert to WGS84 via each floor's georeference control points.
The capture has no typed stairs/elevators, so two vertical links are inferred
where Connection footprints overlap across floors (marked `(inferred)`).

`pois.geojson` → `properties.metadata`, typed as `POIMetadata`
(`app/types/poi.ts`). All fields optional; the card renders what exists.

| Field                       | Shape                                                   | Pointr source                | Mappedin source                  |
| --------------------------- | ------------------------------------------------------- | ---------------------------- | -------------------------------- |
| `category`                  | string                                                  | `typeCode`                   | layer                            |

| `images`                    | string[] (max 3)                                        | `images`                     | —                                |

| `openingHours`              | free text, or `{ "mon-sun": "09:00-21:00" }`            | legacy `openingHours` string | — (galleria uses the range map)  |
| `phone`, `link`             | string                                                  | `phone`, `link`              | `phone.number`, `social.website` |
| `social`                    | `{ facebook, twitter, instagram, … }`                   | —                            | `social` minus `website`         |
| `tags`, `keywords`          | string[] (also indexed by search)                       | `tags`, `keywords`           | `tags`                           |
| `rating`, `numberOfRatings` | number                                                  | same                         | —                                |

## Unified vocabulary (what galleria demonstrates)

| Concept            | Our field                                                      | Pointr                                | Situm                   |
| ------------------ | -------------------------------------------------------------- | ------------------------------------- | ----------------------- |
| Store polygon      | `feature_type: "unit"` + `category`                            | Polygon + `typeCode`                  | POI + category          |
| POI                | Point + `type`                                                 | Point + `typeCode`                    | POI                     |
| Stairs edge        | `network_type: "stairs"`, `is_accessible: false`, `cost: 60`   | `stairs-node`, 60s                    | step types incl. stairs |
| Escalator          | `network_type: "escalator"`, `cost: 45`                        | `escalator-node`, unidirectional, 45s | —                       |
| Elevator           | `network_type: "elevator"`, `is_accessible: true`, `cost: 120` | `elevator-node`, accessible, 120s     | elevator steps          |
| Entrance           | POI `type: "entrance"`                                         | `building-entrance-exit` (1s)         | —                       |

| Turn instructions  | not generated (geometry only)                                  | `message`/`turnAngleRadians` features | indication enum         |

## Route graph conventions (all venues)

- **Weights are seconds.** Walking edges cost distance / 1.2 m/s; connector
  edges carry `cost` in seconds: stairs 60 s/floor, escalator 45 s/floor.
- **Elevators** are a one-off wait plus a short ride: each floor has a stop
  ~1 cm from the corridor anchor, joined by a 45 s boarding edge
  (`from_level_id == to_level_id`), and stops are chained with 15 s hops.
  One floor = 105 s (Pointr's taxonomy says 120 s); six floors = 180 s, so
  long trips take the elevator and 1–2 floor trips take the stairs.
- **Escalators are two-way** unless vendor evidence says otherwise
  (`direction: "forward"` on Harrods' L-1 → L0 and Galleria's central one).
- **Floors never share vertices**: every route coordinate on floor _n_ is
  shifted by _n_ × 2e-7° longitude, so routes can only change floor over a
  connector edge.
- Re-check any re-port with `python3 scripts/audit-venue-routing.py`.

## Known gaps in our engine (from this comparison)

1. ~~**Unidirectional edges** (escalators)~~ — done: `direction: "forward" |
"backward" | "both"` edge property (`graph.ts` honors it).
2. ~~**Turn-by-turn instructions**~~ — done: `routeInstructions` generates
   depart/turn/floor-change/arrive steps with distances
   (`main.ts:buildInstructions`); rendered in the navigation view.
3. ~~**Floor-aware route rendering**~~ — done: routelines are split per level
   and `IndoorDirections.setFloor()` filters them to the active floor.
4. **Turn instructions are angle-based only** — no landmark references
   ("at the food court, turn left") like Pointr's `message` strings.
5. **Indications UX** — Situm-style sequential indication cards
   (INITIAL → TURN → CHANGE_FLOOR → DESTINATION_REACHED) are not yet a
   dedicated UI mode; our steps list is static.
